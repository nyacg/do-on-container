# do-pool v2: alarms, native containers, regions, sleep, facets and sandboxed tenants

v1 proved the cost case: 1,000 always-awake Durable Objects cost $22/month in the pool instead of
$4,050. v2 closes most of the remaining gaps to real DOs and adds a multi-tenant mode for untrusted
code. It builds on Cloudflare's October 2026 container features (the `durable_object` scheduling
policy, filesystem snapshots, the native `ctx.container` API) and on workerd's Worker Loader and
facets.

Running: `do-pool-v2` (edge) + `do-pool-v2-control` (pool). The v1 deployment
(`do-pool.do-pool-lab.workers.dev`) is untouched.

## What changed

**Native containers.** `PoolNodeV2` (`src/pool-node-v2.ts`) extends `DurableObject` and drives
`ctx.container` directly (the `@cloudflare/containers` `Container` class gets no updates after
2026-12-31):

- Image and instance size are chosen at `start()`. The default is a custom 1 vCPU / 2 GiB; `basic`
  isn't accepted under this policy.
- Outbound `http://bridge.internal` goes to the `Bridge` entrypoint via
  `interceptOutboundHttp(..., ctx.exports.Bridge({props}))`.
- A heartbeat alarm keeps the node DO, and with it the container, alive.

**Regions.** The edge Worker maps `request.cf` to a location hint (`wnam`, `enam`, `weur`,
`apac`, …). Placement places *new* objects on a node in that region, creating the node with
`locationHint`. Under the `durable_object` policy the container is scheduled next to its DO: we
measured SJC/IAD/AMS/SIN co-location every time.

**Alarms.**
- The pending alarm is part of every checkpoint and is re-armed on hydration. workerd keeps alarms
  outside the object's tables, so a plain data restore would lose them.
- Objects leaving a node (evict, drain, sleep) hand their alarms to Placement's **alarm registry**.
- A node that dies without draining is recovered from its last manifest, which records each
  object's alarm.
- Placement's own alarm wakes due objects on whichever node owns them.

**Moves are fenced twice.**
- The router answers 410 for an object it's handing off.
- Since v2 the object itself also refuses new requests (410) and waits for in-flight ones before
  its hand-off snapshot. Without this, v1's rollout test lost 1 of 374 acknowledged writes.
- An object moving back to a node it lived on is re-hydrated: per-assignment epochs plus a
  `deleteAll()`/`abort()` retire on the old node.

**Sleep.** An idle node:
1. flushes
2. collects pending alarms
3. takes a filesystem snapshot (`snapshotContainer`, 2.5–4.4 s; crash-consistent under live
   SQLite writes)
4. registers the alarms with Placement
5. stops

The next request, or a due alarm, restarts it from the snapshot with every object's SQLite already
on disk.

**Facets / dynamic code.**
- `FacetHost` (`objects/facet-host.ts`) runs app code loaded by code id through the Worker Loader
  as facet `app`, with its own SQLite.
- A generated shim (`objects/facet-shim-src.ts`) adds checkpoint/restore of the facet's database,
  write tracking, and an alarm proxy, because facets can't own alarms on Cloudflare or in workerd.
- The host-control stub reaches the facet through the dynamic Worker's `env`. Cloudflare rejects
  service stubs in facet *props* with "internal error"; workerd accepts them.
- Publish code with `POST /api/code?app=<id>` (body = module source). Objects are named
  `<appId>:<name>`.

**Examples.** [`examples/`](../examples/README.md) has four apps (counter, notes, chat, reminders) and a playground at `/apps.html` to run each on all three backends, read the source and hot-swap it.

**Sandboxed tenants (`sapp`).** Each app runs in its **own workerd process** inside the node
(`container/spawner.sh`):
- `setpriv` to uid 20000+slot, no capabilities, `no_new_privs`
- `bwrap --unshare-all` (user/mount/pid/net/ipc/uts/cgroup): read-only system, only
  `/data/tenants/<app>`
- **no network**
- Its only egress is a unix socket to the router's `TenantBridge`, which allows its code and
  *its own* checkpoint segments and manifests (names carry `--t--<app>`), and nothing else.

Cost: ~17 MB and ~25 ms to start per tenant process. The probe in `test/lifecycle.test.ts`
(`sandbox-isolation`) checks all of this from *inside* a sandbox. workerd's README says workerd
alone is not a hardened sandbox for malicious code; this puts each tenant behind Linux sandboxing
inside a Firecracker microVM, with a VM-per-tenant tier available by pinning an app to its own node.

## New gotchas (Cloudflare Containers, October 2026)
- **Under `durable_object` scheduling a container dies with its DO instance**, and a deploy
  restarts the script's DOs.
  - Keep the pool in its own control-plane Worker, so ordinary deploys don't touch it.
  - Control deploys restart nodes within ~1–5 minutes, staggered as each busy DO picks up the new
    version.
- Busy DOs take ~5 minutes to pick up a new version. Anything a DO reads from its own code
  (including `ctx.container.images`) lags too. Ask a fresh DO for the current image.
- `basic` isn't a valid instance type under this policy. Custom sizes need ≥1 vCPU.
- `snapshotContainer` works (2.5–4.4 s, 0.4–10 MB). `snapshotDirectory` exists in the experimental
  types but not in production.
- Facets can't set alarms ("Facets currently cannot set alarms"), on Cloudflare or in workerd.
- Cloudflare rejects a service stub in facet props ("internal error"); pass it via the dynamic
  Worker's env instead.
- `AlarmInvocationInfo` isn't serialisable over RPC; copy `{ retryCount, isRetry }`.
- workerd's named Worker Loader entries are never evicted (~2.2 MB each), and `limits.cpuMs` isn't
  enforced there. That's one more reason for a process per tenant.
- A busy pooled node DO kept on old code still runs fine. But under the `durable_object` policy a
  deploy that touches the image *and* the DO code restarts the container anyway, so code-driven
  blue/green (Placement `rollout()`, which works) only matters for nodes whose DOs haven't
  restarted.
